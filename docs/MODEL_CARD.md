# Model Card — MCPGuard tool-description risk model

> Live numbers: `models/model_metadata.json`, `artifacts/metrics/evaluation.json` and the dashboard's **Model Performance** page. They are regenerated by every pipeline run and are deliberately not copied here, so this card cannot go stale.

## Model purpose
Estimates the probability that an MCP tool definition (`tool_name`, `description`, `inputSchema`) will cause AI-agent tool-call failures. It returns a risk score, a risk band, SHAP explanations and documentation recommendations. It is intended as a **pre-deployment review aid** for tool authors and platform teams.

## Model details
| | |
|---|---|
| Type | Gradient-boosted trees (selected automatically; currently XGBoost tuned with Optuna). The selected model is recorded in `model_metadata.json` |
| Input | Tool name, description, JSON input schema |
| Features | Fused vector: TF-IDF word/char n-grams → LSA (64), all-MiniLM-L6-v2 → PCA (48), 26 schema statistics, 25 lexical/naming statistics, 6 engineered risk scores |
| Output | P(agent error), binary prediction at a validation-tuned threshold, risk band (configurable `risk_levels`) |
| Explanations | SHAP TreeExplainer in log-odds; contributions add up exactly to the model logit (tested) |
| Version | `configs/config.yaml → project.version`; dataset `data.dataset_version` |

## Training data
See `docs/DATASET_CARD.md`. The data are real tool definitions (BFCL v3 and MCP reference servers) plus documented augmentations. Labels come from a **controlled simulated-agent benchmark**, not production logs.

## Training procedure
- Stratified grouped split by tool lineage, 70/15/15, with zero group overlap.
- Cost-sensitive learning (`scale_pos_weight`, `class_weight`); no SMOTE.
- Optuna TPE with median pruning on 4-fold grouped CV inside the training split, objective = average precision.
- Selection by validation PR-AUC, then F1, then ROC-AUC; the threshold maximises F1 on validation.
- The test split is used once, for reporting.

## Evaluation
Accuracy, precision, recall, F1, ROC-AUC, PR-AUC, MCC, Brier score and log-loss on train, validation and test. Also: 95% bootstrap CIs, paired bootstrap tests against every baseline, a reliability diagram, a feature-family ablation and slice-based error analysis.

## Intended use
- Ranking and triaging tool definitions before they are exposed to agents.
- Educational and research demonstration of explainable ML on agent tooling.

## Out-of-scope / misuse risks
- **Not a guarantee of agent behaviour.** Real agents (different LLMs, prompts, contexts) may behave differently from the simulator.
- Do not use it as the only gate for safety-critical tools. Do not use it to rank vendors or authors.
- Adversarial gaming is possible: descriptions can be padded with "good-looking" words without becoming clearer. Human review remains necessary.
- Not a security scanner. It does not detect prompt injection or tool poisoning in descriptions.

## Limitations
- The labels' external validity is bounded by the simulator's assumptions (`configs/config.yaml → harness`).
- Some failure modes depend on context outside one definition: sibling tools, user phrasing and server strictness. The error analysis quantifies this.
- The corpus is English and mostly derived from BFCL; other domains or languages may need recalibration.

## Ethical considerations
- No personal data is used. The API stores only a SHA-1 hash of submitted descriptions, never the text.
- All provenance (real, controlled-benchmark, synthetic) is labelled in the data, the API and the UI.
- Metrics are never hard-coded; tests assert that the UI and API serve the exact training outputs.
